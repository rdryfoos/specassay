# SpecAssay — Product Requirements (ID Registry)

This PRD is the **authoritative ID registry** for the `specassay` repo's own
work — the tool dogfooding itself. Founded 2026-08-18 by the docs room
(design-room ruling), scoped explicitly as **founding, not backfill**: no row
below is minted `proven` by declaration. Every ID here rides as **anointed
backlog** (registry entry + one open `**Carries**:` TODO in
`specs/backlog/tasks.md`) until real work picks it up — the registry opens
honest-empty and earns its greens from there, per Rule 6a.

SpecAssay Gate 2 enforces the exact-set rule: the IDs defined here must equal
the IDs referenced in `specs/` and `tasks.md` (the one exception is
*anointed backlog*, an ID carried only by an open TODO).

- FR-DOCS-70 — A version number in a governed document says which kind of claim it is making, and the release refuses one that does not. Four instances of one failure prompted this: a version observed once, typed into a sentence, then left to rot while the thing it described moved, each caught by a person noticing and each later than the last. The mechanism is deliberately not a generator. A generated receipt is unfalsifiable by its reader: they cannot check it against anything, only trust the generator, which makes the documentation a self-report, the one epistemic class this tool exists to refuse. So the receipt stays human-written and the machine refuses it when it lies. Three rules: no unclassified version token in prose, a current claim equals the version being cut, and a dated observation carries an age measured in releases that refuses past a threshold unless the page states why it is kept. The classification is the load-bearing rule; the other two are enforcement on top of a distinction that did not previously exist. Minted 2026-09-18 on a ruling, after the proposed single equality rule was shown to catch only one of the four instances: the README line that started it said "Verified 2026-09-04 ... v0.4.13", which was true, stayed true, and carried its own date. The failure was staleness of relevance, not falsity, and only an age rule sees it. <!-- specassay:stale-ok the record of what was true at v0.4.13; re-observing it would mean re-running on that release, which is not what the sentence claims -->
  - AC-DOCS-20 — Given a governed document containing a version token, when the check runs, then a token carrying none of the accepted classifications is refused naming file, line and token; a token marked as a current claim that does not equal the version being cut is refused; a dated observation more releases behind that version than the threshold is refused unless the page carries a stated reason to keep it; and a quoted range is refused when it disagrees with the bundle manifest.
- FR-DOCS-80 — A mark classifies one claim, and a table row is one claim. A mark covers the block it sits in, which is right for wrapped prose and wrong for a table: a Markdown table is a single block, so a reason written beside one row exempted every other row of the same table. The release step named "Docs must not lie about the version being cut" then passed on documents that did. Found cutting 0.5.6, 2026-10-05, and it had been hiding two real claims: `ONBOARD.md`'s pin table said `v0.5.5` with a current mark while 0.5.6 was being cut, next to a Spec Kit row carrying `stale-ok`; and `docs/submission/README.md`'s own table had said `v0.5.1` with a current mark since 0.5.1, next to a row citing a CHANGELOG section with `stale-ok`. Neither was ever reported. A silent checker is worse than an absent one, because the release trusts it. **Amended 2026-10-06:** a list item is one claim too, and for the same reason. Found by FR-DOCS-90's own rule firing on this registry: `PRD.md`'s rows are list items with no blank line between them, so FR-DOCS-70's `stale-ok` covered every DOCS row written after it, including FR-DOCS-80's.   - AC-DOCS-30 — Given a table or a list whose rows carry different marks, when the check runs, then each row is classified by its own mark alone: a reason beside one row does not exempt the row next to it, a row carrying its own mark keeps it, and a row wrapped onto further lines is still one row. **Authorship**: retrospective.

- FR-DOCS-90 — A reason that no longer describes its claim is not a classification. `stale-ok` says "this old number stays, and here is why", so the one thing it cannot be about is a version equal to the one being cut: that is a current claim, and the reason written beside it belongs to something else. - FR-GATE-90 — Parentage: the Gate derives an optional `parent` edge per row at emit time from the registry document's own heading/section nesting — never authored, never inferred by a viewer, never guessed from ID-prefix naming convention. - FR-GATE-140 — A task is one logical line to every scan, however many physical lines it occupies. A `**Carries**:` list that soft-wraps onto continuation lines carries the same IDs it would carry unwrapped, and the mark itself counts wherever in the task it sits. Refusing would also red every adopter whose `tasks.md` already wraps, on a formatting choice Markdown calls meaningless, and would put the parser's limitation on the author. This tool refuses dishonesty, not typography. Minted 2026-09-20 from the Bang rehearsal on v0.5.1, where three acceptance criteria reported as silent gaps for no reason a reader could find. <!-- specassay:provenance -->

- FR-GATE-150 — A line ending is not a verdict. Every file the Gate writes and then reads again is written with `\n` and read with any `\r` stripped, so the same project reaches the same verdict on Windows as on Linux, and a file that picks up CRLF anywhere between the write and the read still matches. ## CASE

The objective tier, ratified by Rik 2026-09-22 in one line: "Objectives are
minted in CASE.md, cited by stories, refused when orphaned, and the manifest
carries them." This section is that ruling written as intent, minted before
any code, in the practice's own order. The area is named for the document
rather than for the tier deliberately: an area named `OBJ` would sit beside
the `OBJ-` prefix these rows introduce, and `FR-CASE-30` is the row that
forbids reading an edge off an ID family. Naming the two the same thing would
invite the inference it refuses.

Nothing below is proven by declaration. Every row opens as anointed backlog
carried by `T929` in `specs/backlog/tasks.md`, per this registry's founding
scope.

- US-CASE-10 — As someone accountable for why the work exists, I want every story to name the objective it serves, so the thread runs from an outcome I can be held to all the way down to the test that proves it, and a story serving nothing is visible rather than merely unremarked. Today the thread starts at the story: a registry can be entirely green while nobody can say what any of it was for. The tier above story is where that question has an answer that a tool can check, and the reason it belongs in the same machinery rather than in a slide is that an unchecked objective drifts from the work silently, which is the failure this whole tool exists to refuse one level down. **The two documents hold different kinds of thing, ratified 2026-09-22, and reading them alike is the mistake this row exists to prevent.** `CASE.md` holds **bets**, scored later by measures in the world. `PRD.md` holds **promises**, proven by named tests. So a green objective means its promises were kept, not that the bet paid: the CASE paraphrases, the PRD rules. `FR-CASE-60` already says an objective's proof is a question about the world; this says whose question it is, so nobody reads green as paid.
- FR-CASE-10 — A fourth tier above story: **objective**, with IDs of the form `OBJ-<DOMAIN>-NN`, **assigned by the Gate, never typed by a person.** A `CASE.md` author writes headings and prose and nothing else; the first Gate pass that reads an objective without an ID assigns one and **writes it back into the file**, in the same pull-request-visible way `trace-manifest.json` is written. Ruled 2026-09-22, reversing this row's first draft, which had `mint-id.sh` mint objectives the way it mints into `PRD.md`. The reason is the document's audience: a CASE is written by whoever is accountable for the bet, in prose, and asking that person to run a minter before they can finish a sentence puts the registry's machinery in front of the thinking the document exists to hold. A durable ID is still durable; what changes is who types it. **`mint-id.sh` is not the objective minter** and is unchanged by this row: it stays exactly as it is for the `PRD.md` registry. Two things this still touches. The stock `id_regex` admits only `(FR|NFR|AC|US)` as a prefix, so `OBJ-LEND-10` is an ID the current Gate would refuse on sight; the grammar has to admit the new prefix, and a project that has configured its own grammar has to be able to admit it too, per the class settled in 0.5.0 that a configured grammar is consumed as configured. <!-- specassay:provenance --> And a Gate that writes back into a source document is new behaviour for this tool, which has only ever written artifacts: the write has to be as reviewable as any other diff, which is why it lands in the working tree for a human to commit rather than anywhere else.
  - AC-CASE-10a — Given a `CASE.md` objective heading carrying no ID, when the Gate runs, then it assigns the next `OBJ-<DOMAIN>-NN` for that domain and writes the ID back into `CASE.md`, so the file on disk afterwards carries the ID the manifest reports.
  - AC-CASE-10b — Given a `CASE.md` objective that already carries an ID, when the Gate runs, then that ID is kept exactly as written and the file is not rewritten on account of it.
  - AC-CASE-10c — Given a `CASE.md` whose objectives are reordered, renamed, or interleaved with new ones, when the Gate runs, then every existing objective keeps the ID it already had and only the objectives without one are assigned to: **the Gate never renumbers.**
- FR-CASE-20 — A second registry path in the config (`CASE.md` beside `PRD.md`), read by the Gate under the same exact-set rules one level up. The rule that binds registry, specs and tasks at the story tier binds objectives and stories at the tier above it, with the same two-sided refusal: **a story that names no objective is an orphan**, and **an objective that no story names is backlog, visible, not a gap**. That asymmetry is the whole design and is stated here so nobody softens it later: an unserved objective is a promise nobody has started, which is honest and common, while a story serving nothing is work whose reason has gone missing, which is the condition worth surfacing. Reading a second document is not the same as reading the first one twice: the two registries have different tiers, different mint sites and different owners, and the config has to say which is which rather than leaving the Gate to infer it from a filename. **Objectives are read by heading, under the CASE template's "What are you betting?" question, and any numbering a person adds to those headings is decoration the reader ignores** (ruled 2026-09-22). The template's nine questions are headings; whether a given `CASE.md` numbers them is a house style, and a registry that keyed on the number would make one house style a requirement and silently lose every objective written in the other.
  - AC-CASE-20a — Given a config naming both an ID registry and an objective registry, when the Gate runs, then it reads both, and the set of objectives it knows is exactly the set defined in the objective registry, with the same duplicate and orphan refusals the ID registry already gets.
  - AC-CASE-20b — Given an objective that no story cites, when the Gate runs, then that objective is carried as `backlog` and named in the run's own output, and the run does not fail on account of it.
  - AC-CASE-20c — Given two `CASE.md` files identical except that one numbers its question headings and the other does not, when the Gate runs on each, then both produce the same objective rows, with the same IDs and the same statements.
- FR-CASE-30 — The citation is declared, never inferred. A story names its objective either by a declared line in the spec (`Serves: OBJ-LEND-10`, parallel to `**Carries**:` and `**Retires**:`) or by nesting under it in the registry document, and by nothing else. **No edge is ever read off an ID family:** `US-LEND-10` and `OBJ-LEND-10` share a domain and that is all they share. This is the same rule `FR-GATE-90` already holds for parent derivation, where the reason was written down at the time: an inferred edge is a guess that renders identically to a fact. The domain-grouping convention remains a display fallback for a reader with no edges, and never becomes an edge.
  - AC-CASE-30a — Given a spec carrying a well-formed `Serves:` line naming one or more objectives, when the Gate runs, then the story's objective edges are exactly the objectives that line names.
  - AC-CASE-30b — Given a registry document where a story is nested under an objective, when parent derivation is enabled, then the objective is the story's parent by the same nesting rule every other tier already uses.
  - AC-CASE-30c — Given a story and an objective sharing a domain, with no `Serves:` line and no nesting between them, when the Gate runs, then no edge is derived between them and the story is treated as serving no objective.
- FR-CASE-40 — The refusal for an orphan story ships **report-only**, in `gate.diagnostics[]`, and ratchets to blocking per project the way `block_uncovered_proof` already does. The reasoning is the same as it was there, and it is not timidity: a real registry carries a backlog of orphan stories the first time this runs, because the tier did not exist when those stories were written. A check that reds every adopter on first contact is a check they turn off, and a check nobody runs refuses nothing. Report-only makes the backlog visible and countable; the per-project switch is how an estate that has burned the backlog down keeps it down. This row promises both halves: the diagnostic now, and the switch that makes it a refusal on a project's own word.
  - AC-CASE-40a — Given a story naming no objective, when the Gate runs with the objective registry configured and the ratchet unset, then the run records the orphan story in `gate.diagnostics[]`, names the count in its output, and `gate.ok` is unchanged by it.
  - AC-CASE-40b — Given the same project with the ratchet set, when the Gate runs, then an orphan story is a failing finding and the run fails.
- FR-CASE-50 — The manifest carries objective rows: `tier: "objective"`, parents from the citation rather than from the document alone, and a rollup computed by the ratified colour rule. **The rule, ratified 2026-09-22, written here so viewers do not each invent one:** a parent's colour is the weakest *started* child among `GAP`, `tracked-debt` and `proven`, in that order of weakness; `backlog` and `retired` are counted but not coloured; and a parent with no started child is `backlog`. The rule goes into `docs/trace-manifest-v5.md`'s rollup section, which is where a viewer looks, and not only into this row. This matters more than it looks: the rollup already present is a count, and a count does not tell a renderer what colour to paint. Every viewer that has wanted one has so far had to decide for itself, which is how two renderings of one manifest come to disagree, and a manifest whose readers disagree is the capture-method failure `PROMOTION-CONTRACT.md` rule 12 names.
  - AC-CASE-50a — Given a project with objectives and stories citing them, when the Gate emits the manifest, then each objective is a row with `tier: "objective"` whose children are exactly the stories that cite it, by the citation and not by domain.
  - AC-CASE-50b — Given an objective whose started children include at least one `GAP`, when the rollup is computed, then the objective's rolled-up colour is `GAP`; given started children that are all `proven`, then `proven`; given no started child at all, then `backlog`, with `backlog` and `retired` children counted in the totals either way.
  - AC-CASE-50c — Given `docs/trace-manifest-v5.md`, when read at the rollup section, then the colour rule is stated there in full, so a viewer implementing it needs no access to this registry.
- FR-CASE-60 — Objective-level proof may be a **measure** rather than a test: a key result with a named source, the way an acceptance criterion's proof is a named passing test. **Named here as a later ID, deliberately not built**, so that the tier's shape does not exclude it. The constraint this places on `FR-CASE-10` through `FR-CASE-50` is the whole reason it is minted now rather than later: nothing in the tier's first build may assume that proof is a test, that a proof lives in a test file, or that an unproven objective is awaiting a test. An objective's proof is a question about the world, and the world is not in the repository. What a source is, how a measure is captured, and how stale a measure may be before it stops counting are all open and are not promised by this row.

## REL

Release cut lines, ratified in principle 2026-09-22 and **sequenced behind
the objective tier**, not shipping with it. Minted in the same PR for intent
so the two are read together, because a release name is a second axis across
the same rows and the two designs constrain each other; built separately,
because the tier is the harder half and this one is cheap once the row shape
has settled.

- FR-REL-10 — A registry row may carry `Release: <name>`. The registry holds the short list of release names it recognises; the Gate checks the tag exact-set against that list, the same way it checks every other set it reads, so a row tagged for a release nobody declared is a refusal rather than a new release; the manifest carries the release as a row field; and **a row with no release is unscheduled backlog**, which is a statement about the plan rather than about the work. A free-text tag would make a typo into a silent second release, and a release that exists because somebody misspelled one is exactly the kind of quiet drift the exact-set rule exists to catch. Deliberately not promised here: any ordering between releases, any date, and any notion of a release being complete. This row promises a name, a closed list, a check and a field.
  - AC-REL-10a — Given a registry declaring its release names, when a row carries a `Release:` naming one of them, then the manifest's row for that ID carries that release name.
  - AC-REL-10b — Given a row carrying a `Release:` naming a release the registry does not declare, when the Gate runs, then it fails with a finding naming the row and the undeclared name.
  - AC-REL-10c — Given a row carrying no `Release:` at all, when the Gate runs, then the run does not fail on account of it and the row is reported as unscheduled.
