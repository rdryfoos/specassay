# SpecAssay — Product Requirements (ID Registry)

This PRD is the **authoritative ID registry** for the `specassay` repo's own
work — the tool dogfooding itself. Founded 2026-08-18 by the docs room
(design-room ruling), scoped explicitly as **founding, not backfill**: no row
below is minted `proven` by declaration. Every ID here rides as **anointed
backlog** (registry entry + one open `**Carries**:` TODO in
`specs/backlog/tasks.md`) until real work picks it up — the registry opens
honest-empty and earns its greens from there, per Rule 6a.

SpecAssay Gate 2 enforces the exact-set rule: the IDs defined here must equal
the IDs referenced in `specs/` and `tasks.md` (the one exception is
*anointed backlog*, an ID carried only by an open TODO).

- FR-GATE-10 — `--matrix`: regenerate a human-readable coverage table (`coverage.md`) + SVG summary bar (`coverage.svg`) from the current registry/gate state. **Boundary line (design commitment, stated before build):** `--matrix` is a portfolio-snapshot renderer, not a second viewer. It reads the same already-computed data the Gate just derived — never re-scans, never re-derives status logic of its own — and writes two static, committed artifacts meant for a cold reader with no Loupe running: a CI log, a PR diff, a README badge. No live interactivity, no browser, no drift risk beyond ordinary file staleness: CI enforces the golden thread via the Gate script itself, every push, regardless of whether `coverage.md`/`coverage.svg` were regenerated that push. If the SVG and Loupe's live rendering of the same manifest ever disagree, the manifest is what's wrong, not either renderer. Reads `trace-manifest.json` (v4, the frozen four-status file) — `retired` rows are absent from `rows[]` there by design (`FR-GATE-30`), so the matrix never needs a fifth bar segment. Colors and canonical ordering are the family's own status tokens (`INTERFACE-CANON.md` §2: backlog `#9ed4ff` → tracked-debt `#c9903a` → proven `#219653` → GAP `#eb5757`, GAP last), not invented locally. Self-dating: the SVG carries the manifest's own `generatedAt` timestamp as visible text, the same discipline every other family artifact with a "when was this true" claim already follows. Modeled on HomesFlow's own bespoke `--matrix` mode (`scripts/check-traceability.sh`, pre-canon prior art for the structure — summary table, per-type sections, generated-file banner — not for its legacy colors) — feature parity here is this repo's own named trigger for that fork's retirement.

  - AC-GATE-10b — Given the emitted SVG, when inspected, then its status-color segments use exactly the family's canonical tokens and ordering (backlog `#9ed4ff` → tracked-debt `#c9903a` → proven `#219653` → GAP `#eb5757`), and its visible text carries the manifest's own `generatedAt` timestamp.

This fence is recorded here specifically so nobody reads `FR-GATE-20` as having already answered the cross-repo question.

- FR-GATE-30 — `retired`: a genuine fifth status alongside proven/tracked-debt/backlog/GAP, distinguishing an intent withdrawn on purpose from a silent GAP. There is no settable status field: `retired` derives entirely from an explicit, dated, reasoned, append-only retirement record on an open task — `**Retires**: <id-list> (<YYYY-MM-DD>): <reason>`, parallel to `**Carries**:` — checked ahead of every other status branch, for any type (US/FR/NFR/AC). Version boundary: `trace-manifest.json` (v4) freezes at exactly four status values (a published schema with strict validators); a retired row leaves v4's `rows[]` entirely rather than carry a value v4 never declared, and the same information moves to a new top-level `retired: [{id, date, reason}]` list instead, so nothing disappears silently. `trace-manifest.v5beta.json` carries `retired` as a normal fifth row status from the start. A malformed retirement record (no parseable ID, or no `(YYYY-MM-DD): reason` tail) refuses loudly before any scanning, the same discipline as `FR-GATE-70`. Minted 2026-08-18 (HomesFlow's first intent retirement, `US/FR/AC-CLEW-01`), design settled 2026-08-20 across two design-room rulings after a modeling proposal (four options weighed; a genuine fifth status won on the evidence already in `docs/backlog.md`'s "Pattern candidate" section) and a self-audit correction on the v4 export mapping. Built citing `docs/backlog.md`'s four-legs framework (registry annotation, spec anchor, carry task, gap-vs-withdrawn at proof) and HomesFlow's own hand-improvised tombstone convention as prior art.
  - AC-GATE-30a — Given an open task carrying a well-formed `**Retires**:` record naming one or more registry IDs, when the Gate runs, then every named ID's status is `retired` in `trace-manifest.v5beta.json`'s `rows[]`, regardless of its proof or pending state.

- FR-GATE-80 — `proofs[]`-population (the `test_ac_regex` scan feeding `proof_by`/the manifest's `proofs` field) matches anywhere in a test file's text, including comments, with no structural check that the match sits on a real test — and no filtering against the passing-testcase set even when `test_results` (Rule 6a) is configured, unlike `status_for()`'s own `tested` set, which inherits that filter. - FR-GATE-90 — Parentage: the Gate derives an optional `parent` edge per row at emit time from the registry document's own heading/section nesting — never authored, never inferred by a viewer, never guessed from ID-prefix naming convention. Per-project opt-in via `parent_derivation: heading-nesting | none` in config; a flat spec (or `none`) emits no edges, and absence renders as absence (em-dash law), not a guess. Document structure yields a tree by construction — single-parent v1, for free; multi-parent/DAG deferred until a real cross-cutting case forces it. Every row with descendants carries a composition rollup over **all rows in its subtree, at any depth** — not leaves-only: a non-leaf's own status counts alongside its descendants', so a mid-tier `GAP` or `backlog` can't vanish from an ancestor's rollup the way a leaves-only count would let it (ratified rationale: an invisible gap is the one failure class this system exists to prevent). The rollup carries a total row count alongside its per-status counts, so a renderer can name its basis ("N rows") rather than imply a single meaning for a mixed-depth count. **Cited invariant, not incidental:** the recursive rollup is cycle-safe only because single-parent holds (a tree has no cycles by construction); anyone relaxing single-parent to a DAG later must revisit rollup safety before shipping it, not discover it in production. Minted 2026-08-20 from `docs/hierarchy-parentage-brief-2026-08-20.md` (design room, two-question ruling — derivation mechanism and tree-vs-DAG were closed by the brief's own "Resolution on population" section; rollup basis and sequencing ruled separately the same day), citing the acceptance criterion that forced this brief: "if I can't find code and test from intent, then this whole system does not really help me" (Loupe's descent on `US-UNBIND-10` dead-ending at "No proof" despite real proof three levels down, on `AC-UNBIND-10/20/30`). Sequenced behind DIG and `T905`/`T906` (parentage rides behind the emission work it resembles); anointed backlog until then. The Loupe-side COMPOSITION card that renders this edge is out of this repo's scope, scheduled separately — nothing here blocks on it: the edge ships in the manifest whether or not a viewer renders it yet.
  - AC-GATE-90a — Given a registry document with heading/section nesting and `parent_derivation: heading-nesting` configured, when the Gate runs, then each nested row's manifest entry carries a `parent` edge to its enclosing row, and a flat document (or `parent_derivation: none`) carries no `parent` edges at all.
  - AC-GATE-90b — Given a row with descendants at more than one level deep, when the manifest is emitted, then that row's composition rollup counts include every descendant row at every depth, not only its direct children, and include the row's direct children's own statuses too (not only their descendants').
  - AC-GATE-90c — Given any row's composition rollup, when the manifest is emitted, then the rollup carries a total row count alongside its per-status counts.
- FR-GATE-100 — Cold-install on-ramp: the Gate talks a first-time installer through its own state instead of leaving them to infer it. Three parts. (1) An empty registry (0 IDs) still exits 0, but the closing line says the registry is empty, that nothing is promised yet, that the Gate stays green until something is, and names the two on-ramps to a first ID with runnable commands: greenfield (mint before the Spec Kit spec; the preset makes specs inherit IDs from the registry) and brownfield (mint one ID against a requirement in a doc that already exists; no backfill). (2) The Python interpreter is detected, never hardcoded: `SPECASSAY_PYTHON`, then `python3`, then `python`, each probed for 3.8 or newer; none usable is a one-line FAIL with an install hint, exit 2, before any scanning. (3) The script reports its own config state at startup, every run: the config path it found and how, or that it is missing, that it is running on `config-template.yml` defaults, and the one `cp` command that scaffolds it. Minted 2026-09-03 from the first Windows cold install on record (senior engineer, Git Bash, no Spec Kit experience, brownfield repo with specs under `docs/**`): his run ended at `OK (0 registry IDs)` with no idea what came next, his box had `python` but no `python3`, and he could not tell whether install had scaffolded the config.
  - AC-GATE-100a — Given a registry file with zero definition lines and an otherwise clean run, when the Gate finishes, then it exits 0 and its closing output states the registry is empty, that the Gate stays green until a first ID exists, and gives runnable next steps for both a greenfield and a brownfield first mint.
  - AC-GATE-100b — Given a machine where `python3` is absent or unusable but `python` is Python 3.8 or newer, when the Gate runs, then it completes on `python` and reports which interpreter it used; given neither is usable, then it fails before any scanning with exit 2 and a one-line install hint, and writes no manifest.
  - AC-GATE-100c — Given any run, when the Gate starts, then it reports the config path it resolved and how; given the config file is missing, then it names the missing path, states it is running on `config-template.yml` defaults, and prints the copy command that scaffolds it.
