# SpecAssay — Product Requirements (ID Registry)

This PRD is the **authoritative ID registry** for the `specassay` repo's own
work — the tool dogfooding itself. Founded 2026-08-18 by the docs room
(design-room ruling), scoped explicitly as **founding, not backfill**: no row
below is minted `proven` by declaration. Every ID here rides as **anointed
backlog** (registry entry + one open `**Carries**:` TODO in
`specs/backlog/tasks.md`) until real work picks it up — the registry opens
honest-empty and earns its greens from there, per Rule 6a.

SpecAssay Gate 2 enforces the exact-set rule: the IDs defined here must equal
the IDs referenced in `specs/` and `tasks.md` (the one exception is
*anointed backlog*, an ID carried only by an open TODO).

- FR-GATE-30 — `retired`: a genuine fifth status alongside proven/tracked-debt/backlog/GAP, distinguishing an intent withdrawn on purpose from a silent GAP. There is no settable status field: `retired` derives entirely from an explicit, dated, reasoned, append-only retirement record on an open task — `**Retires**: <id-list> (<YYYY-MM-DD>): <reason>`, parallel to `**Carries**:` — checked ahead of every other status branch, for any type (US/FR/NFR/AC). Version boundary: `trace-manifest.json` (v4) freezes at exactly four status values (a published schema with strict validators); a retired row leaves v4's `rows[]` entirely rather than carry a value v4 never declared, and the same information moves to a new top-level `retired: [{id, date, reason}]` list instead, so nothing disappears silently. `trace-manifest.v5beta.json` carries `retired` as a normal fifth row status from the start. A malformed retirement record (no parseable ID, or no `(YYYY-MM-DD): reason` tail) refuses loudly before any scanning, the same discipline as `FR-GATE-70`. Minted 2026-08-18 (HomesFlow's first intent retirement, `US/FR/AC-CLEW-01`), design settled 2026-08-20 across two design-room rulings after a modeling proposal (four options weighed; a genuine fifth status won on the evidence already in `docs/backlog.md`'s "Pattern candidate" section) and a self-audit correction on the v4 export mapping. Built citing `docs/backlog.md`'s four-legs framework (registry annotation, spec anchor, carry task, gap-vs-withdrawn at proof) and HomesFlow's own hand-improvised tombstone convention as prior art.
  - AC-GATE-30a — Given an open task carrying a well-formed `**Retires**:` record naming one or more registry IDs, when the Gate runs, then every named ID's status is `retired` in `trace-manifest.v5beta.json`'s `rows[]`, regardless of its proof or pending state.
  - AC-GATE-30b — Given the same retired ID, when `trace-manifest.json` (v4) is emitted, then that ID does not appear in `rows[]`, appears exactly once in a top-level `retired` list with its date and reason, and `statusCounts` carries exactly the four original keys (no `retired` key).
  - AC-GATE-30c — Given a `**Retires**:` record with no parseable registry ID or no `(YYYY-MM-DD): reason` tail, when the Gate runs, then it refuses before any scanning and writes no manifest.
- FR-GATE-40 — `orphan-covers` gains domain scoping consistent with `orphan-spec` and `orphan-task`, so `@covers` detection distinguishes use from mention: marks inside fenced code blocks, documentation files, and the checker's own comments are not live marks. Minted 2026-08-18, citing the DOCS-room founding finding: `docs/**` had to be excluded from the assayer's own self-governance because the Gate could not yet read its own documentation without believing it (`docs/docs-gaps.md`).
  - AC-GATE-40 — Given a docs file quoting an `@covers` line as a teaching example, when the Gate runs with docs in `src_globs`, then no `orphan-covers` finding derives from the quotation.
  - AC-GATE-41 — Given `check-traceability.sh`'s own source, when scanned, then its comments and regex definitions never self-match.
- FR-GATE-50 — The manifest emitter dedupes `implementations` (and `proofs`) on `(id, normpath, line)` before writing the manifest, so the same mark reached twice (overlapping `src_globs` entries, or a `./x` vs `x` path spelling) is listed once. Minted 2026-08-18, citing a real emit where 62 of 100 rows carried duplicated implementations.
  - AC-GATE-50 — Given the same `@covers` mark reachable via two overlapping `src_globs` entries or a `./x` vs `x` path spelling, when the manifest is emitted, then that mark appears exactly once in `implementations`.
- FR-GATE-70 — A list-type config key (`src_globs`, `test_globs`, or any later `yaml_list()` consumer) that's present but malformed (an inline YAML array) or bare (no items under it) refuses loudly before any scanning, instead of silently parsing to an empty list. Minted 2026-08-19: the self-referential case of the silent-gap shape this tool exists to refuse in adopters' own work — found twice in one day, once in the docs room's own reproduction recipe and once in the capture session that followed it.
  - AC-GATE-70a — Given a list-type config key written as an inline array, when the Gate runs, then it refuses before any scanning: stderr names the key, quotes the offending raw line, shows the accepted block-style shape, and points at the troubleshooting entry — no `trace-manifest.json` is written.
  - AC-GATE-70b — Given a list-type config key present with no items under it, when the Gate runs, then it refuses the same way, and the message states plainly that omitting the key entirely is what means "none."
  - AC-GATE-70c — Given a list-type config key absent from the file entirely, when the Gate runs, then behavior is unchanged: an empty list, no refusal.
- FR-GATE-60 — An additive `provenVia` (delegated-proof) field on FR/US rows, naming the AC(s) whose proof stands in for a row that carries no `@covers`/test of its own, so Loupe's PROOF stage can render the chain instead of "No proof." Minted 2026-08-18, design-room proposal, considered not built: **open design question** — the registry has no existing FR→AC parent/child edge (shared ID-domain prefix is a naming convention, not a declared relationship), so `provenVia` needs either (a) an explicit author-declared link (e.g. a `**Provenvia**:`/registry-annotation grammar, honest but one more thing to write) or (b) an inferred one (the emitter guesses from domain/statement adjacency, convenient but a real risk of a false chain — exactly the kind of self-report Rule 6a exists to refuse). No AC yet; needs that ruling first.
- FR-GATE-80 — `proofs[]`-population (the `test_ac_regex` scan feeding `proof_by`/the manifest's `proofs` field) matches anywhere in a test file's text, including comments, with no structural check that the match sits on a real test — and no filtering against the passing-testcase set even when `test_results` (Rule 6a) is configured, unlike `status_for()`'s own `tested` set, which inherits that filter. Minted 2026-08-20, citing a SpecCost engine finding (not acted on there — SpecCost doesn't own this code, this repo does): `AC-WALK-10`'s `proofs[]` lists `test_AC_WALK_10_new_activity_reflected_with_no_separate_refresh`, a name that survives only inside a rename-explanation comment after the real test was renamed (2026-08-18 mark-provenance audit, T016). No status-integrity risk — `status_for()`'s protected path already keeps `AC-WALK-10` honestly `tracked-debt` — but a legibility/trust defect on a field whose whole job is being trustworthy at a glance, and the same root cause as `FR-GATE-40` (text-matching where structural/execution-matching is required), one call site over. Verified directly against this repo's own `check-traceability.sh` (lines ~330–347): `test_acs.txt` is `cut` straight from the same unfiltered `proof_hits.txt` that populates `proof_by`, not independently derived. Recommend building alongside any future `FR-GATE-40`-family work rather than as a separate pass — one root cause, two call sites.
  - AC-GATE-80 — Given `test_results` is configured and a test name matches `test_ac_regex` only inside a comment (not a real, currently-passing test), when the manifest is emitted, then that name does not appear in the ID's `proofs[]`.
- FR-GATE-90 — Parentage: the Gate derives an optional `parent` edge per row at emit time from the registry document's own heading/section nesting — never authored, never inferred by a viewer, never guessed from ID-prefix naming convention. Per-project opt-in via `parent_derivation: heading-nesting | none` in config; a flat spec (or `none`) emits no edges, and absence renders as absence (em-dash law), not a guess. Document structure yields a tree by construction — single-parent v1, for free; multi-parent/DAG deferred until a real cross-cutting case forces it. Every row with descendants carries a composition rollup over **all rows in its subtree, at any depth** — not leaves-only: a non-leaf's own status counts alongside its descendants', so a mid-tier `GAP` or `backlog` can't vanish from an ancestor's rollup the way a leaves-only count would let it (ratified rationale: an invisible gap is the one failure class this system exists to prevent). The rollup carries a total row count alongside its per-status counts, so a renderer can name its basis ("N rows") rather than imply a single meaning for a mixed-depth count. **Cited invariant, not incidental:** the recursive rollup is cycle-safe only because single-parent holds (a tree has no cycles by construction); anyone relaxing single-parent to a DAG later must revisit rollup safety before shipping it, not discover it in production. Minted 2026-08-20 from `docs/hierarchy-parentage-brief-2026-08-20.md` (design room, two-question ruling — derivation mechanism and tree-vs-DAG were closed by the brief's own "Resolution on population" section; rollup basis and sequencing ruled separately the same day), citing the acceptance criterion that forced this brief: "if I can't find code and test from intent, then this whole system does not really help me" (Loupe's descent on `US-UNBIND-10` dead-ending at "No proof" despite real proof three levels down, on `AC-UNBIND-10/20/30`). Sequenced behind DIG and `T905`/`T906` (parentage rides behind the emission work it resembles); anointed backlog until then. The Loupe-side COMPOSITION card that renders this edge is out of this repo's scope, scheduled separately — nothing here blocks on it: the edge ships in the manifest whether or not a viewer renders it yet.
  - AC-GATE-90a — Given a registry document with heading/section nesting and `parent_derivation: heading-nesting` configured, when the Gate runs, then each nested row's manifest entry carries a `parent` edge to its enclosing row, and a flat document (or `parent_derivation: none`) carries no `parent` edges at all.
  - AC-GATE-90b — Given a row with descendants at more than one level deep, when the manifest is emitted, then that row's composition rollup counts include every descendant row at every depth, not only its direct children, and include the row's direct children's own statuses too (not only their descendants').
  - AC-GATE-90c — Given any row's composition rollup, when the manifest is emitted, then the rollup carries a total row count alongside its per-status counts.

## DIG

Archaeology mode, rung (a) of the three-rung ladder (no-LLM floor only;
local-model and user-supplied-API-key rungs are explicitly out of scope).
Built 2026-08-20 per `docs/archaeology-mode-build-handoff-v1-2026-08-20.md`
(receipted by version line before this mint).

- US-DIG-10 — As a stranger dropped into an unfamiliar, undocumented repo, I want a first-pass structural read of its likely intent/behavior/proof shape, so I have a starting map instead of nothing.
- FR-DIG-10 — `specassay dig [path]` command: static, no-LLM heuristics over test names/bodies, routes/API surface, module/directory structure, README/docs prose, and commit history propose a first-pass candidate registry — written only to `dig-report.json`, flat data the Gate never loads, never chains, never governs anything with. There is no `--anoint` flag on this command; turning a proposed row into a real, dated, minted registry row is separate, later, human work. **Amended 2026-08-21:** the default output location is the operator's current working directory, never the scanned target path and never a session-scratch directory — found running the command for real against an external, read-only clone (`github.com/SpecDriven/insurance-java`, per the archaeology-mode build handoff), where the report was first written to a session scratchpad "under our own control" per the handoff's own §0 caution about not writing into the target, except a scratchpad is cleanup-eligible and not actually durable. A receipt whose evidence sits in cleanup-eligible ground is a claim on a timer, not a record — the tool's own default now makes the durable choice the easy one instead of leaving it to whoever invokes it that session.
- FR-DIG-20 — Dig-report schema: each row carries a type guess (US/FR/AC/NFR), statement text, `epistemicClass: "inferred"` (constant, always present, never omitted), provenance (source kind, file, line, and for test-derived rows the test's own name), a confidence signal, and a suggested area (derived from directory structure, not emitted as its own row type). Document-level: generator version, source repo path, generated-at timestamp, and source commit when available.
  - AC-DIG-10 — Given any target repo, when `dig` runs (dry-run or real), then no write touches any file outside the configured output path — no exceptions, no `--anoint` flag exists.
  - AC-DIG-20 — Given `--dry-run`, when `dig` runs, then it prints row counts by type and source and writes nothing at all, not even a partial file.
  - AC-DIG-30 — Given no `--out` override, when `dig` runs, then the report is written to `dig-report.json` in the operator's current working directory, not the scanned target path — the default output location depends on where the operator invoked the command from, never on what path they pointed `dig` at.
